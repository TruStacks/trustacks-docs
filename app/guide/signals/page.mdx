# Signals

**Where:** **Signals** in the sidebar (`#/signals`).

{/* screenshot-placeholder: Signals with the Sources panel (GitHub "Connected · read-only verified", ArgoCD "Reporting", SARIF upload) above the findings list, one finding selected showing the six-step governed loop. Save as public/guide/signals.png */}

Signals is where security findings meet the governed delivery loop.
TruStacks is not a scanner and does not own the fix. Findings come from the
tools you already run (Snyk, Trivy, Dependabot, GitHub Advanced Security, a
SARIF file), or are observed in GitHub by your runner's read-only
[MCP Signals](/reference/mcp-server#mcp-signals) source. TruStacks governs, validates and ships the fix through your
pipeline. You approve, always. TruStacks re-proposes; it never auto-merges.

## Sources

A **Sources** panel sits at the top of the screen. It lists every place
findings and observations come from, each with the status your runner last
reported. With no report, it says **Not connected** or **No reports yet**,
never "connected".

| Source | What it reads | Status shown |
|---|---|---|
| **GitHub, read-only** | Dependabot, code-scanning and secret-scanning alerts, and CI runs, read by your runner with a read-only token | **Not connected**; **Connected · read-only verified · last sweep …**; **Refused** (the server offered a tool we do not allow); **On, but its Secret is missing in the runner's namespace**; **Last sweep failed** |
| **ArgoCD deploy status** | Whether a merged change synced and became healthy, read by your runner | **No reports yet** or **Reporting · last report …** |
| **SARIF upload** | Any scanner's SARIF output (CodeQL, Semgrep, Trivy, and so on) | **Upload a file any time** |

A source that is not reporting yet has a **Connect** button; SARIF has
**Upload**. **Connect a source** at the top of the panel opens the same
wizard with a source chooser first.

### Connect a source

The wizard never asks for a credential. TruStacks writes the commands; you
run them on your own cluster.

1. **Choose a source**: GitHub, read-only; ArgoCD deploy status; or SARIF
   upload.
2. **Pick the runner.** Choose one of your connected runners, then enter its
   **Runner namespace** and **Helm release** (default `trustacks-runner`).
   For ArgoCD, also enter the namespace your ArgoCD Applications live in
   (default `argocd`). These values only fill in the commands; they are not
   sent anywhere. If no runner is connected, the wizard sends you to
   [enroll one](/guide/runners) first. The GitHub source needs runner
   0.2.14-rc27 or later; an older runner is stopped here with a prompt to
   upgrade it from **Runners**.
3. **Run the commands.**
   - For GitHub: create a fine-grained personal access token scoped to the
     repos you have connected, with read-only repository permissions only
     (Actions, Contents, Metadata, Pull requests, Issues, Dependabot alerts,
     Code scanning alerts, Secret scanning alerts). Store it with the
     generated `kubectl` command. It reads the token with `read -rs`, so it
     never appears on screen or in your shell history, and pipes it to
     `kubectl` on standard input. `printf` is a shell builtin, so the token
     never becomes a process argument; `--from-literal` would put it in
     `kubectl`'s arguments, where anyone who can list processes (`ps`) could
     read it:

     ```bash
     read -rs GH_TOKEN && \
     printf '%s' "$GH_TOKEN" | kubectl -n <runner-namespace> create secret generic trustacks-mcp-github \
       --from-file=token=/dev/stdin && unset GH_TOKEN
     ```

     Then turn the source on. The `--version` is pinned to the version that
     runner runs now, so the upgrade neither up- nor downgrades it:

     ```bash
     helm upgrade <release> oci://ghcr.io/trustacks/charts/runner --version <runner-version> -n <runner-namespace> \
       --reset-then-reuse-values \
       --set mcpSignals.enabled=true \
       --set mcpSignals.sources.github.enabled=true
     ```

     The runner needs HTTPS egress to `api.github.com`.
   - For ArgoCD: the same `helm upgrade` with
     `--set observer.enabled=true --set observer.argocdNamespace=<namespace>`.
     The chart grants the runner read-only `get, list, watch` on ArgoCD
     Applications and nothing else.
4. **Wait for the report.** After **I've run them**, the wizard waits for
   *that runner's own* report and shows exactly what came back:
   **Connected · read-only verified**, **Refused**, the Secret missing, or
   **Last sweep failed**. If nothing arrives within 10 minutes, it tells you
   to check that the runner pod restarted and to look in its logs.

### Upload a SARIF file

{/* screenshot-placeholder: Connect a source, SARIF upload: the file picker and the "Uploaded. N findings created." result. Save as public/guide/signals-sarif-upload.png */}

Choose **SARIF upload** (or **Upload** on its row) and pick a `.sarif` or
`.json` file. The file is posted to the findings intake; each result becomes
a finding, and the list refreshes. The wizard reports how many findings were
created, or that the file had no results. The file is read as data, never
executed.

## Findings

### No findings yet

When nothing has reported a finding to your workspace, the screen shows
**No findings yet** and lists how findings arrive: GitHub, read-only through
your runner, and any scanner by SARIF upload. If the findings list fails to
load, the screen says so ("Couldn't load findings"), rather than showing an
empty list.

### Your findings

When at least one finding exists, a green strip reads **Live · N from
your sources**.

- **Incoming findings (left)**: each with a severity chip (CRIT, HIGH,
  MED, LOW), title, source and age. A finding an MCP source observed shows
  its source as **MCP feed · github**.
- **The selected finding (right)**:
  - a header card: the finding's id, source, **observed by** (for example
    `mcp:github`, for a finding seen by a read-only source in your runner
    and re-checked every sweep), fix source (if any) and when it was
    detected;
  - **actions**: **Triage** on a new finding; **Propose a fix** on a
    triaged finding whose repo is connected; **Dismiss** on anything not
    finished. Finished findings show **Validated** or **Dismissed** instead;
  - **The governed loop**: six steps (Finding detected, Coordinator
    triages, Crew proposes fix, Constitution decides, You approve, ArgoCD
    ships + validates) with the current one highlighted;
  - if the finding's repo is not governed by TruStacks yet, **This repo
    isn't governed by TruStacks yet** with **Connect this repo →**;
  - **Proposed fix**: who authored the fix, or a note that the crew has
    not proposed one yet;
  - **Transition history**: every state change, oldest first.

## What it means

- **Triage** says a human has looked at the finding and it is real.
- **Propose a fix** starts a governed proposal for the service the finding
  belongs to: the DevOps Engineer drafts the change, it is validated and
  judged by the constitution, and a PR opens on your platform repo. It only
  works when the finding's repo is connected as a service in an
  Application, and that service has been analyzed. Otherwise the app says
  to connect the repo and run an analysis first.
- **Dismiss** closes the finding with no further action. It stays in the
  history.

Findings are not a second policy. A proposed fix gets the same
validation, constitution check and human review as any other proposal.

## What to do here

1. Triage new findings.
2. For a real issue in a connected service, **Propose a fix**, then review
   the resulting proposal and PR. Signals does not link to the proposal yet;
   find it on the service's **Proposals** tab under
   [Applications](/guide/applications#proposals).
3. Dismiss noise, so the [Overview](/guide/overview) queue only shows what
   needs you.

## How it connects

- Untriaged findings and fixes awaiting approval appear on the
  [Overview](/guide/overview) queue.
- A proposed fix is a normal [proposal](/guide/applications#proposals).
- **Connect this repo →** opens the [connect wizard](/guide/applications#connecting-repos).

## Beta limits

- **Two intake paths.** Findings arrive from the read-only GitHub source
  (open Dependabot, code-scanning and secret-scanning alerts on repos
  connected to an Application) and from SARIF uploads, plus the API (a
  SARIF endpoint and a generic findings endpoint). Each GitHub alert enters
  Signals once, however many sweeps see it. Repos added only through
  `extraRepos` never produce findings. Snyk and Trivy integrations are
  direction, not shipped; their output arrives today as SARIF.
- **The approve-and-ship steps are not built on this screen.** The
  approve button on **Proposed fix** reads **Approve & ship, coming soon** and is
  disabled. Approval happens where it always does: on the pull request.
- The live **Proposed fix** card still says governed-loop transitions
  "land in a follow-on slice", even after **Propose a fix** has started a
  real proposal. Trust the loop stepper and the transition history.
