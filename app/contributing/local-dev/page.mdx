# Local development

Local development runs the entire TruStacks platform from source on a k3d
cluster on your laptop: the control plane and its Postgres database, Zitadel
for sign-in, the runner, the UI, Gitea as the Git host, ArgoCD, and Zot as
the registry for signed policy bundles. It needs access to the private
`trustacks-mvp` repo and is for people working on TruStacks itself.

<Callout type="warning">
  **Not the customer path.** Customers use the hosted service and install
  only the runner. See the [Quickstart](/getting-started/hosted-quickstart).
  Local development differs from hosted in ways that matter: the control
  plane dispatches work *into* the runner (push mode), Git is Gitea with SSH
  deploy keys, and policy is signed with a project-local key.
</Callout>

## What gets installed

All reachable through Traefik on `*.localtest.me:8080` (`localtest.me`
resolves to `127.0.0.1`; no `/etc/hosts` edits):

| Service | URL | Purpose |
|---|---|---|
| UI | `http://ui.localtest.me:8080` | The product UI |
| Control plane | `http://cp.localtest.me:8080/healthz` | API, audit, event streams |
| Runner | `http://runner.localtest.me:8080/healthz` | The agent crew |
| Zitadel | `http://zitadel.localtest.me:8080` | Sign-in (the same identity provider as hosted) |
| Gitea | `http://gitea.localtest.me:8080` | In-cluster Git host, standing in for GitHub |
| Argo CD | `http://argocd.localtest.me:8080` | GitOps controller watching the sample platform repo |
| Zot | `http://zot.localtest.me:8080/v2/` | OCI registry for signed policy bundles |

Plus two Postgres instances, each on its own PVC: one for the control plane
(`postgres:16`, installed by the control-plane chart) and one for Zitadel
(the `trustacks-postgres` release). They are deliberately separate, so a
Zitadel upgrade can't pin or break the control plane's database. There is no
SQLite mode any more.

## Prerequisites

On macOS:

```bash
brew install --cask docker            # Docker Desktop, then start it
brew install k3d helm kubectl uv node opa oras cosign
```

`make doctor` checks for all of them: `docker k3d helm kubectl uv node npm
opa oras cosign`. Minimum versions:

- **k3d** 5.8+
- **helm** 3.14+
- **kubectl**, current
- **uv** (Python toolchain)
- **node** 20+ with npm
- **opa** 1.x (Rego tests and bundle builds)
- **oras** 1.3+ (pushes the policy bundle to Zot)
- **cosign** 3.x (signs the bundle; the runner verifies it)

You also need an **Anthropic API key** (OpenRouter works too) and access to
`github.com/TruStacks/trustacks-mvp`:

```bash
git clone https://github.com/TruStacks/trustacks-mvp.git
cd trustacks-mvp
```

## Bring-up

### 1. Configure your environment

```bash
cp .env.example .env
# set ANTHROPIC_API_KEY=<your-key>
```

### 2. Install language dependencies

```bash
make install
```

### 3. Bring up the cluster

```bash
make up
```

Creates the k3d cluster, installs Gitea, ArgoCD, Postgres, Zitadel and Zot,
builds the control plane, runner and UI images locally, imports them into
k3d, deploys them, and applies your key to the runner. It takes a while. If
it fails at the secrets step, the cluster is still up: set the key and run
`make secrets`.

### 4. Seed

```bash
make seed
```

Idempotent; re-run it any time. In order, it:

1. Applies the cosign public key as the `policy-pub-key` ConfigMap.
2. Runs the Rego tests, builds the constitution bundle, pushes it to Zot with
   `oras`, and signs it with the project-local key in `.policy-keys/`
   (generated on first run by `make policy-keys`).
3. Seeds Gitea with the sample service repos (FastAPI, Spring Boot, .NET, Go)
   plus the platform and overlay repos.
4. Provisions per-repo SSH deploy keys and a Gitea API token as Secrets the
   runner loads.
5. Registers connection profiles in the control plane.
6. Applies the ArgoCD root Application, which watches the platform repo's
   `argo-apps/` directory **recursively**. Anything the DevOps Engineer merges
   under `argo-apps/argo-apps-<cluster>/` becomes a child Application.
7. Bootstraps Zitadel: creates the TruStacks project and OIDC client, and
   writes `.zitadel-bootstrap/` locally, then seeds the local workspaces.
8. Rolls the runner so it picks up the new keys and bundle.

### 5. Sign in

```bash
make urls            # every URL, plus the ArgoCD admin password
make zitadel-admin   # Zitadel admin login for the UI
make seed-token      # a machine-user token for curl against the control plane
```

## Run the crew

From the UI, open a seeded service, click **Run analysis**, then **Promote to
proposal**. Or from the CLI (the local control plane accepts it without a
token; the hosted service does not):

```bash
cd runner && uv sync
uv run trustacks review sample-app-gitea           # Code Reviewer; prints the analysis id
read -r -p "Analysis id printed above: " ANALYSIS_ID
uv run trustacks plan "$ANALYSIS_ID" --dry-run     # DevOps Engineer, no PR
uv run trustacks plan "$ANALYSIS_ID"               # opens a PR in Gitea
```

A proposal runs artifact validation, then the policy gate against the
Zot-pulled constitution, then an advisory gap check, then opens the PR on the
`platform` repo in Gitea. A deny stops before the PR and names the rules.

## How local differs from hosted

### Push mode

Locally the control plane runs with `dispatchMode: push`: it calls the runner
in-cluster. Hosted runners use pull mode (they enroll with a token and
long-poll `api.trustacks.com`). Some control-plane endpoints that proxy to the
runner only work in push mode. Keep that in mind before assuming a feature
that works locally also works hosted.

### Credentials

| Credential | Local form | Provisioned by |
|---|---|---|
| LLM key | Secret `trustacks-runner-llm` (legacy `trustacks-runner-secrets` is imported on first control-plane boot) | Settings in the UI, or `.env` + `make secrets` before the control plane is up |
| Git access | Per-repo SSH deploy keys: Secrets labeled `trustacks.io/role=git-deploy-key` and `trustacks.io/repo=<repo>`, mounted under `/var/run/secrets/git/<repo>/` | `make seed` (`scripts/setup_runner_access.py`), or the Gitea branch of the connect wizard |
| PR API | Secret `gitea-api-token` | `make seed` |
| GitHub App (optional) | Secret `trustacks-github-app` with `app-id`, `private-key.pem`, `webhook-secret`, plus `TRUSTACKS_CP_GITHUB_APP_SLUG` on the control plane | You, by hand, against a test App |

Deploy keys are read-only on service and overlay repos and read-write on the
platform repo. New keys are picked up by rolling the runner; no `helm
upgrade` needed.

### Policy signing

Locally the bundle is signed with the **project-local** cosign key in
`.policy-keys/` (gitignored) and verified by the runner's `load-policy-bundle`
init container against the `policy-pub-key` ConfigMap. Hosted runners verify
keylessly against the public `trustacks-policy` publishing workflow instead.

If the pull or verification fails (Zot wiped, key mismatch), the runner falls
back to the copy baked into its image and records why. To load an unsigned
bundle while debugging, set `policyBundle.verify=false`; never in anything
customer-facing.

## Common operations

- **Tear down:** `make down` deletes the cluster. `make up && make seed`
  brings it back.
- **Rotate the LLM key:** Settings in the UI, or update `.env` and run
  `make secrets`.
- **After editing policy:** `make policy-bundle` (or `make seed`) rebuilds,
  pushes and signs. Otherwise the runner keeps the previous bundle.
- **After a Zot restart:** Zot has no persistence. Re-run `make seed`; until
  you do, the runner uses its image-baked policy.
- **Logs and status:** `make logs`, `make status`. The local runner
  Deployment is `runner-runner` in `trustacks-system`.
- **Before committing:** `make check` runs lint, typecheck, and tests. The
  control-plane tests need Docker (they run against `postgres:16`).

## Troubleshooting

| Symptom | Fix |
|---|---|
| `make up` fails at the secrets step | `ANTHROPIC_API_KEY` is missing from `.env`. Set it and run `make secrets`. |
| `Permission denied` cloning from Gitea | Deploy keys and Secrets are out of sync. `make seed`, then roll the runner. |
| Rules page is empty | Locally the control plane asks the runner for its rules (push mode), so check the runner is up (`make status`) and what its `load-policy-bundle` init container loaded. Both the signed bundle and the image-baked fallback carry the rule inventory; `make policy-bundle` republishes the bundle if Zot was wiped. |
| First proposal denied by policy | The gate working. The `policy_check` event lists the rule ids; see the [constitution](/reference/constitution). |
| Zitadel pods crash-loop after an upgrade | Its Postgres is pinned below 18 on purpose; don't bump it. See the comments in `scripts/bootstrap-k3d.sh`. |
